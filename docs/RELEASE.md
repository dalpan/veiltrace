# Release Engineering and Supply Chain (M4.2)

## 1. Commands
```bash
npm ci --ignore-scripts          # exact, lockfile-pinned install (install scripts are not needed)
npm run release                  # development build → release/ (releaseType "development"; dirty trees allowed and recorded)
npm run release:candidate        # release candidate: refuses a dirty or uncommitted tree; records the clean source commit
npm run release:verify           # integrity + production-policy checks; exit code 0 = pass
npm run release:repro            # two independent clean builds (fresh copies, npm ci --offline); compares outputs
npm run supply-chain             # SBOMs, license review, lockfile check, npm audit → release/supply-chain/
npm run supply-chain -- --offline   # same without npm audit (registry access)
```
`release/` is git-ignored: artifacts are regenerated, never committed.

## 2. What a release contains

| File | Purpose |
|---|---|
| `veiltrace-chromium-<version>.zip` | Production build (`dist/extension` layout): manifest, popup, content script, icons |
| `release-manifest.json` | Product, extension version, default and experimental engine versions, extractor version, source commit and dirty flag, `SOURCE_DATE_EPOCH`, toolchain (Node, esbuild), permissions, per-file SHA-256 and size, artifact SHA-256 |
| `veiltrace-chromium-<version>.cdx.json` | **Artifact SBOM** (CycloneDX 1.5): the distributed extension, Apache-2.0, SHA-256 of the ZIP, source commit, `components: []` (no third-party code) |
| `SHA256SUMS` | SHA-256 of the ZIP, the artifact SBOM and the release manifest (`shasum -a 256 -c` compatible) |

**Release types.** `development` (default) may come from a dirty tree, and the manifest says so (`source.dirty`). `candidate` requires a clean, committed tree. **No artifact is labelled "official":** an official release additionally requires signed distribution, which does not exist yet (DEPLOYMENT.md §5). The development artifact built during M4.2 (from a dirty tree) is not a release.

`verify-release` checks:
- every checksum, the manifest hashes of every file inside the ZIP and the ZIP CRCs;
- that the ZIP holds exactly the listed files;
- production policy: permissions exactly `activeTab` + `scripting`; no host permissions, content scripts, background, `externally_connectable` or web-accessible resources; not a test build; `connect-src 'none'`; no network, `eval` or messaging identifiers in the JavaScript;
- the artifact SBOM matches the ZIP hash, declares Apache-2.0 and lists no components;
- no third-party code markers inside the artifact (`Mozilla Public License`, `lightningcss`, `node_modules`);
- a `candidate` was not built from a dirty tree.

**Integrity is not authenticity.** Anyone who can replace the ZIP can also replace SHA256SUMS and the manifest. Authenticity requires signed distribution (DEPLOYMENT.md §5) or an out-of-band trusted copy of SHA256SUMS.

## 3. Reproducibility
- **Sources of determinism:**
  - pinned dev dependencies and lockfile;
  - esbuild output;
  - icons generated by a pure function;
  - a ZIP writer with sorted entries, a fixed timestamp (`SOURCE_DATE_EPOCH` = last commit time), fixed permissions and no extra fields;
  - JSON written with stable key order.
- **Verified 2026-10-21:**
  - Two independent clean copies of the source tree, each with `npm ci --offline`, produced byte-identical SHA256SUMS (ZIP and manifest).
  - Two builds in the same tree also matched (`tests/release.test.ts`).
  - The ZIP passes `unzip -t`.
- **Known inputs that change the output (by design):** the source commit and dirty flag, `SOURCE_DATE_EPOCH`, and the Node and esbuild versions recorded in the manifest. A different esbuild version may also change the bundle. Release builds must be made from a clean commit (`dirty: false`); development builds record `dirty: true`.
- **Scope of the reproducibility claim:** verified only on **macOS / arm64, Node 26.8.1, npm 11.19.0, esbuild 0.28.2**. Other operating systems, CPU architectures and Node/esbuild versions are **untested**. The esbuild native binary is platform-specific, so cross-platform identity is plausible but unproven.
- Source commit metadata does not break determinism: both builds receive the same commit, dirty flag and `SOURCE_DATE_EPOCH` (from the commit) and produce identical outputs.

## 4. Supply chain (2026-10-21)

| Item | Result |
|---|---|
| Runtime dependencies | **0**. The shipped bundle contains only first-party code (no imports from `node_modules` in `src/core`, `src/extract` or `src/extension`). Runtime SBOM has 0 components |
| Toolchain SBOM | CycloneDX 1.5 (`npm sbom`): the **build/test toolchain as installed on this machine**, 150 components (`release/supply-chain/sbom-toolchain.cdx.json`; timestamp pinned, random serial removed). The lockfile lists 199 entries: the difference is optional platform-specific packages (e.g. esbuild/rollup/lightningcss binaries for other OSes) that npm does not install on macOS/arm64. A toolchain SBOM made on another platform will differ in exactly those entries |
| Artifact SBOM | Per release (`veiltrace-chromium-<version>.cdx.json`): the distributed extension only, no components, hash-bound to the ZIP |
| Lockfile | v3, 199 entries, all with `integrity`, all from `registry.npmjs.org`, all dev-only. Direct dev dependencies pinned to exact versions |
| Vulnerability audit | `npm audit`: 0 info / 0 low / 0 moderate / 0 high / 0 critical (point-in-time result; re-run per release) |
| Install scripts | Not needed for building: release builds succeed after `npm ci --offline --ignore-scripts` (verified by `release:repro`). npm 11 also left the scripts of `esbuild` (postinstall) and `fsevents` unexecuted in the development install, and the full test suite passes there |

## 5. Signing and distribution (future requirement)
Release signing is **required before any official distribution** and is not implemented. Until then, there are four risks:
- whoever controls the distribution point can replace the ZIP, the SBOM, the manifest and SHA256SUMS together;
- users of "Load unpacked" see developer-mode warnings and can modify the unpacked files locally;
- there is no automatic update or revocation channel;
- the extension ID of unpacked installs depends on the install path.

Plan: DEPLOYMENT.md §5 (offline-generated CRX3 key, signed CRX, internal update manifest, two-machine reproducible build comparison before signing).
